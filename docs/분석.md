## 2. UTM — 결론: 지금은 하지 말 것

### 왜 불필요한가

1. **세부키워드 결정에 필요한 데이터는 네이버가 이미 준다.** 노출·클릭·CTR·CPC·비용은 광고관리자 키워드 리포트에 UTM 없이 다 나옴. UTM이 추가로 주는 건 "그 키워드로 온 사람이 사이트에서 뭘 했나"뿐.
2. **표본이 없다.** 3일간 광고 레퍼러 유입 3세션. 키워드 5개로 쪼개면 키워드당 0~1건 = 노이즈. 최소 키워드당 30~50클릭 필요.
3. **전환 추적이 불안정하다.** (위 1번 이슈) 전환을 못 세는데 유입만 쪼개봐야 판단이 안 섬.

### UTM에 대한 흔한 오해 (정리)

**UTM은 탐지가 아니라 라벨이다.** 내가 URL에 직접 써넣은 글자가 되돌아오는 것뿐.
네이버는 구글의 `{keyword}` 같은 자동 치환이 없어서 **키워드마다 URL을 손으로 만들어야 함.**

| 궁금한 것 | UTM으로 가능? |
|---|---|
| 어느 도메인에서 왔나 | UTM 없어도 됨 (이미 보임) |
| 내가 등록한 광고 키워드 중 뭘 눌렀나 | ✅ UTM 필요 |
| **사용자가 검색창에 실제로 친 말** | ❌ **UTM으로도 불가** |
| 자연검색 유입의 검색어 | ❌ **영원히 불가** |

네이버가 `Referrer-Policy: strict-origin`을 걸어서 검색어가 지워진 채 도착함. 실측 확인:
```
https://m.search.naver.com/     ← ?query=... 없음
https://m.ad.search.naver.com/  ← 광고인데도 검색어 없음
```
3일치 24세션 전부 이 상태.

### 실제 검색어를 보려면 (UTM 아님)

1. **네이버 검색광고 → 검색어 보고서** — 키워드 확장으로 유입된 실제 검색어. **세부키워드 발굴엔 이게 정답.**
2. **네이버 서치어드바이저** — 자연검색 노출/클릭 검색어
3. **구글 서치콘솔** — 구글 자연검색

### 언제 UTM을 도입하나

광고 클릭이 **하루 20~30건 이상** 쌓이고 **전환 추적이 복구된 뒤**.

## 3. 비즈채널 반려 문제 — 해결 완료 ✅

### 증상

```
사유(https://www.onsia.city/yamok-grandhill)
(PC) 접속 시 표시URL과 다른 URL로 이동하는 경우는 광고할 수 없습니다.
(모바일) 동일
```

### 원인 — UTM 때문이 아니었음

```
https://www.onsia.city/yamok-grandhill  →  301  →  https://야목역서희스타힐스.xyz/
```

표시URL과 실제 도착 도메인이 달라서 걸린 것. **리다이렉트는 원래부터 있었고**, 연결URL을 건드리면서 재검토가 트리거돼 잠자던 문제가 드러난 것.
→ 연결URL을 원복해도 사유가 사라지지 않는 구조였음.

### 해결

비즈채널 웹사이트 주소를 **`.xyz` apex(punycode)** 로 변경:

```
xn--w52b01jv7aa057aotah02dmgmlja.xyz
```

⚠️ **www 붙이면 안 됨** — `www.xn--...xyz`도 apex로 301 튕겨서 같은 사유로 재반려.

실측 검증:
```
https://www.onsia.city/yamok-grandhill        → 301 → .xyz
https://www.xn--w52b01jv7aa057aotah02dmgmlja.xyz/ → 301 → apex
https://xn--w52b01jv7aa057aotah02dmgmlja.xyz/     → 200 (리다이렉트 없음) ✅
   + UTM 파라미터 붙여도 PC/모바일 둘 다 200
```

**상태: 수정 완료, 광고 정상 노출 중.**

### (참고) 나중에 UTM 쓸 때의 URL 형식

스킴 빼고 입력 (네이버 입력창에 `https://` 드롭다운이 이미 있음):

```
# PC
xn--w52b01jv7aa057aotah02dmgmlja.xyz/?utm_source=naver&utm_medium=cpc&utm_campaign=powerlink&utm_term=%EC%95%BC%EB%AA%A9%EC%97%AD%EC%84%9C%ED%9D%AC%EC%8A%A4%ED%83%80%ED%9E%90%EC%8A%A4&utm_content=pc

# 모바일
xn--w52b01jv7aa057aotah02dmgmlja.xyz/?utm_source=naver&utm_medium=cpc&utm_campaign=powerlink&utm_term=%EC%95%BC%EB%AA%A9%EC%97%AD%EC%84%9C%ED%9D%AC%EC%8A%A4%ED%83%80%ED%9E%90%EC%8A%A4&utm_content=mobile
```

`utm_term`은 `야목역서희스타힐스` percent-encoding. 직원 명함용 `?a=` 파라미터와 충돌하지 않음.

**추이도 완전 평탄** (4,789 → 4,970, 1년간 무변동, 시즌 피크 3월 +12%).

## 5. 실행 계획 (광고)

### 즉시 추가

| 키워드 | PC 입찰 | 모바일 입찰 | 근거 |
|---|---|---|---|
| **비봉서희스타힐스** | 최소 | **주력** | 모바일 CTR 7.47%, 효율 1위(5.95%) |
| **화성아파트분양** | **OFF/최소** | **주력** | 7월 PC 검색 0회, 모바일 93~100% |

시작 입찰은 낮게. 신규 키워드는 볼륨이 작아 높게 부를 이유 없음.
(지난 `야목역서희스타힐스` CPC 2,751원이 지출 42%를 잡아먹은 전례)

### 정리

**끌 것**: 안산 계열 전부(`안산아파트` 포함), `비봉지구`, `화성비봉`, 봉담 계열 전부

**입찰 조정**:
- `야목역서희스타힐스그랜드힐`(CTR 4.93%) ← 예산 이동. 같은 물건인데 `야목역서희스타힐스`(CTR 1.74%, CPC 2,751원)가 지출이 더 많았음
- `야목서희스타힐스`(CTR 7.37%), `야목역서희일반분양`(CTR 40%) — 노출 95회/5회뿐. 입찰가 낮아 밀리는 중 → **올릴 가치 있음**

**보류 (판단 필요)**: `비봉예미지2차` (450회, 효율 3.38%)
경쟁 단지 중 유일하게 효율 양호. 타겟은 완벽하나 **상표권 리스크**.
→ 하려면 **키워드만 사고 소재에 "예미지" 절대 미사용** 조건.

**전 키워드 공통**: 모바일 비중 67~100% → **PC 입찰 최소화, 모바일 집중**

### 3~5일 후 검증

1. **네이버 키워드 리포트** — 신규 2개의 실제 CTR/CPC. 마피아넷 평균(7.47%/4.84%)과 비슷 → 확대, 절반 이하 → 중단
2. **트래커** — `node --env-file=.env scripts/yamok-3days.mjs 5`
   세션 수 / 평균 체류 / 0초 이탈률을 현재 baseline(24세션, 평균 48초~1분58초)과 비교

## 7. 마피아넷 기술 구조 분석 (벤치마킹용)

> 대상: https://ma-pia.net — 네이버 키워드 검색량 조회 도구
> 방법: Playwright로 네트워크 요청·응답·프론트 소스 리버스 엔지니어링

### 7-1. 스택

| 레이어 | 정체 |
|---|---|
| 웹서버 | nginx + PHP |
| **CMS 베이스** | **그누보드5 (GnuBoard5) + APMS 테마** |
| 프론트 | **jQuery 3.7.1** — React/Vue/Next 전혀 없음 |
| 차트 | Chart.js 2.9.4 + datalabels + zoom + hammerjs, 일부 자체 SVG 렌더링 |
| 수익화 | AdSense + GA4 + UA(레거시) + GTM + 네이버 wcslog |

근거: `g5_url`, `g5_bbs_url`, `g5_is_member`, `g5_bo_table`, `/bbs/logout.php`, `bootstrap-apms.min.css`

**그누보드5 게시판 CMS 위에 커스텀 PHP를 얹은 구조.** 회원/로그인은 그누보드 기본 기능, 키워드 도구만 직접 구현.
SPA 아님 — 서버가 PHP로 HTML 껍데기를 뿌리고 jQuery가 위젯별 AJAX로 채움.

### 7-2. API 맵

`/analysis/naver/?q=키워드` 한 페이지가 11개 엔드포인트를 병렬 호출:

| 엔드포인트 | 역할 |
|---|---|
| `api/naver/keyword_info.php?keyword=&totalSum=` | 쇼핑카테고리·월간블로그·포화도 |
| `api/naver/month_search_volume_change.php` | **12개월 추이** (schemaVersion 2) |
| `api/naver/content_data.php` | 블로그/카페/뷰 발행량 + 포화도 |
| `api/naver/is_adult.php` | 성인 키워드 판정 |
| `api/naver/search_gender.php` | 성별 |
| `api/naver/month_search_wekely.php` | 요일별 *(오타 그대로)* |
| `api/naver/month_search_ages.php` | 연령대 |
| `naver/content_api.php?q=&ts=&ci=&pd=` | 검색결과 1페이지 섹션 구조 |
| `naver/blog_top_api.php` | 상위 블로그 5 (글자수/이미지수/발행일) |
| `naver/cafe_top_api.php` | 상위 카페 5 |
| `naver/google_serp_api.php` | 구글 SERP (큐 방식) |
| `api/v2/google/keywords.php?action=lookup` | 구글 Ads 검색량/CPC |

**연관 키워드 10개는 각각 `keyword_info.php`를 또 호출** → 한 페이지에 20~30개 요청.
위젯 하나가 실패해도 페이지는 뜨는 설계.

### 7-3. ⭐ 배울 점 1 — 데이터랩 상대지수 → 절대 검색량 역산

**이 사이트의 핵심 기술.**

```json
{"period":"2025-08", "ratio":100,
 "pcSearchCnt":383.07693760601643,
 "mobSearchCnt":7962.728638894599,
 "totSearchCnt":8345}
```

소수점 15자리 = **계산된 값**이라는 결정적 증거.

- **네이버 데이터랩 API**: 12개월 추이를 주지만 **상대지수(0~100)만**. 절대 검색량 없음.
- **네이버 검색광고 API**: 절대 검색량을 주지만 **이번 달만**. 추이 없음.

→ 둘을 곱해 **12개월 절대 추이를 합성**. 어느 API도 단독으로 못 주는 데이터를 만들어냄.

### 7-4. ⭐ 배울 점 2 — 크롤링 차단 우회 = DB 작업 큐 + 별도 수집 PC

```json
{"ok":false, "queued":true, "job_id":54043,
 "job_status":{"status":"pending","attempts":"0",
               "locked_by":"","locked_at":null,
               "last_error":"","result_count":"0"},
 "blocked":true,
 "message":"구글이 서버 수집 요청에 확인 페이지를 반환했습니다. 수집 PC 작업 큐에 등록했습니다."}
```

구조:
1. 서버(데이터센터 IP)가 구글 크롤링 시도 → **캡차 차단**
2. 실패 시 **DB 작업 큐 테이블에 job 등록**
3. **가정용 IP의 실제 PC**가 큐를 폴링해 대신 수집
4. `locked_by`/`locked_at` = **비관적 락 워커 패턴** (중복 처리 방지)
5. `attempts`, `last_error` = 재시도 + 에러 추적

**→ 우리 크롤러(`crawl-homepage-universal.mjs` 등)에 바로 적용 가능.**
현재는 실패하면 그냥 종료 → 큐 + 재시도 + 락 구조를 넣으면 견고해짐.

### 7-5. ⭐ 배울 점 3 — 캐시 계층

```json
"time":"0.03520703 초 걸림"
```

0.035초는 외부 API 왕복이 물리적으로 불가능한 속도 → **DB 캐시 히트.**
키워드별 결과를 저장해두고 재사용. URL의 `time=1785901733201`은 브라우저 캐시 버스팅용.

### 7-6. 허술한 점 (반면교사)

1. **API 전부 GET + 사실상 무인증.** 브라우저 콘솔 `fetch()`로 전량 추출 가능. rate limit이 클라이언트 팝업 수준
2. **같은 데이터를 두 API가 다르게 응답.** `content_data.php` 카페 포화도 67.90% vs `content_api.php` 0 → 레거시/신규 병존. 새로고침마다 화면 숫자가 바뀜 (카페 발행량 0 ↔ 1,684 실제 관측)
3. **오타가 프로덕션에** — `month_search_wekely.php`
4. **JSON인데 content-type이 `text/html`**
5. **디버그 정보 노출** — 서버 실행시간, `job_id`, `last_error`가 응답에 그대로
6. **CSP가 `report-only`** — 실질 방어 없음
7. **구글 Ads 토큰 만료 방치** — `{"error":"토큰 발급 실패"}`
   → 구글 데이터가 전부 `-`로 나온 건 키워드에 검색량이 없어서가 아니라 **저쪽 서버 장애**

### 7-7. 우리가 만든다면

필요한 건 **네이버 API 3개 조합**:

| API | 얻는 것 | 비용 |
|---|---|---|
| 네이버 **검색광고 API** (키워드도구) | 절대 검색량, CTR, 클릭수, 경쟁도, 연관키워드 | 무료 (사업자 계정 — **보유 중**) |
| 네이버 **데이터랩 API** | 12개월 상대추이, 성별/연령/기기 | 무료 |
| 네이버 **검색 API** | 블로그/카페 발행 건수 → 포화도 계산 | 무료 |

설계안:
```
Next.js 15 Server Component
  └ Supabase site 스키마에 keyword_cache 테이블
      (keyword, payload jsonb, fetched_at)
  └ 캐시 히트 → 즉시 반환 / TTL 만료 → 재수집
  └ 상위노출 블로그는 기존 크롤러 파이프라인 재활용
```

기존 자산과 대부분 겹침(Supabase, Prisma, 크롤링 파이프라인, 캐시 패턴).
**신규 개발은 API 클라이언트 3개 + 역산 로직 정도.**
